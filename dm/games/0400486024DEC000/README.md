# The Legend of Zelda: Ocarina of Time (`0400486024DEC000`)

A Switch 2 game: update v131072, SDK 22.2.8 (`Ounce`). Nintendo EPD's engine (sead, agl, gsys, Havok, CRIWARE; project `Owl`, with Tears of the Kingdom's file layout) on NVN2. Modules `main`, `subsdk0` (NintendoSDK_movie) and `sdk`; one rewriter patch, the frame step ([`patches.py`](patches.py)). Status: plays on the Mac through the title, the opening, a new file's first scene, Link's house and Kokiri Forest, with saves, at about 59 fps with the picture close to console video. Mac only so far.

## What it needs

| Setting | Where | Why |
|---|---|---|
| `mem_reserve 0x320000000`, `mem_alias 0x100000000`, `mem_stack 0x10000000`, `app_pool 0x240000000` | [`game.tsv`](game.tsv) | the game asks `SetHeapSize` for 0x18ce00000; the rest as Donkey Kong Bananza, the Switch 2's 9 GB |
| `mem_map_limit on` | [`game.tsv`](game.tsv) | a map past the application pool fails with ResultLimitReached, as on Horizon. The SDK's allocator keeps freed pages mapped until a map fails, then gives them back ([PR 1444](https://github.com/seedds/nxnative/pull/1444) reports a black screen leaving the Deku Tree without it; not reached here) |
| `sys_resource 0x3000000` | `game.tsv` | 48 MB, as the NPDM declares |
| `render_cond on` | `game.tsv` | agl clears a copy of the prepass depth again under a render condition the console skips. Run unconditionally, the opaque pass's `EQUAL` test fails everywhere ([PR 1299](https://github.com/seedds/nxnative/pull/1299)'s finding) |
| `gpu_timestamps segment` | `game.tsv` | the game's dynamic resolution decides from GPU timestamps, and with one time per submission it never lowers its resolution ([why](../../../docs/reference/frame-rate.md#dynamic-resolution-that-never-moves-and-draw-passes-that-wait-for-each-other)) |
| Dynamic-resolution stub | [`patches.py`](patches.py) (frame step rule, `others`) | full resolution unless the launcher's Dynamic resolution is on ([Dynamic resolution](#dynamic-resolution)) |
| `draw_barriers game` | `game.tsv` | about 180 full barriers a frame NVN does not ask for: GPU 25 → 18 ms at full resolution |
| `tex_flush_upload on`, `tex_dirty_upload on` | `game.tsv` | as Tears of the Kingdom: the CPU writes the terrain tiles' height (R32F), blend and hole (RGBA8) maps into textures after creating them. Without the keys those textures stay zero: flat blue holes in the ground around the path with grass floating in them, and grey stone where the console shows dirt |
| `fps_target 60`, `MATCH_FRAME_STEP` | `game.tsv`, [`patches.py`](patches.py) | the game steps its time by a frame ratio, its base rate / its frame rate, whatever the frame took: below 60 fps it ran in slow motion. The ratio takes the host's step (1 vsync at 60 fps, 2 where 60 does not hold), so game time follows real time ([why](../../../docs/reference/frame-rate.md#a-fixed-frame-step-plays-in-slow-motion-on-a-slow-mac)); the same stub holds the dynamic resolution at full size unless `DM_DYNAMIC_RESOLUTION=1` |
| `shader_groups`, `shader_note` | `game.tsv` | shaders grouped as `/Shader/`, `/Effect/`, `/Lib/`, `/UI/` |
| `pad_layout full` | `game.tsv` | a 3D field and both sticks |

One [NUP container](../../../docs/development.md#the-packing-script-in-detail) of 25.6 GB: `scripts/pack_nup.py` unpacks it to `extract/v131072/`. The RomFS keeps most files as zstd with dictionaries from `Pack/ZsDic.pack.zs`. The movies are AV1.

## Frame rate

### Game speed and the frame step (current)

- The interpolator gets colour only. What else it could take, from an outdoor frame's pass dump: the scene's depth is there (D32F, 683x384), and agl's depth-linearisation pass (`agl_common.sharcb`, fragment `247836a7c2c52254`, writing an R32F copy) has the camera's near plane, far plane and aspect ratio at the start of its uniform block (0.1, 25000, 1.778): a lead for the camera, in agl's shared library rather than this game's code. Motion vectors: none. The game never calls NVN2's DLSS, and its upscaler to the 2048x1152 picture is `agl_ndsr_vr_light` compute (`a335c1db6270c355`, then `d99fbeeb53d38847` writing the picture), which reads the scene colour and a 683x384 intermediate the earlier `agl_ndsr_vr` passes made, no velocity. The other path is the matrices (macOS 27: worldToView / viewToClip, from which MetalFX derives the camera's motion), from the scene's uniform block. The UI: drawn into the 2048x1152 picture after the upscaler (UI textures in the next passes), which a last pass draws into the 2560x1440 window texture; the host has only the final picture, so a generated frame moves the HUD with what lies under it (MetalFX's `uiTexture` needs the UI alone: the split is the first pass after `d99fbeeb53d38847` writes the picture). Steps 2 and 3 of the plan (depth and camera, the UI apart) are not done.
- Cost: MetalFX's interpolator works at the drawable's size (2560x1440 on this Mac's window): 7.9 ms p50 / 12 ms p95 of present GPU time per generated picture; on a standalone test 3 ms at 683x384, 3–8 ms at 1280x720, 8–9 ms at 1920x1080 (an idle GPU's low clock makes these vary). Interpolating at the game's picture size before the present's scaling would save about half. On a GPU-bound game this time comes out of the frame's budget: outdoors, where 30 does not hold, it would lower the game's frame rate.

## Dynamic resolution

- The controller (v131072; found by fingerprint, so the addresses are only for reading): the parameters are `game__gfx__DynamicResolutionParam` (`LoadThreshold`, `ReduceCounterMax`, `IncreaseCounterMax`, and a list of levels, each a `ResolutionReduceScale` and a `Priority`). Once a frame the update (`main+0x805aa0`) reads the frame's GPU time, subtracts what its cost model predicts at the current size and keeps the trend of that residual. The level function (`main+0x8065e0`) adds the residual to the model's cost at each level and returns the best level under the threshold: 0, the full 1536x864, when the current size fits. The update moves down after `ReduceCounterMax` frames that ask for it and back up after `IncreaseCounterMax`. Scripted `GPULoad` hints from event data (`main+0x31c3de0`) and `OneshotSetDynamicResolutionLoadThreshold` adjust it in cutscenes.
- Resolved on the host: after a loading screen it sat at its floor, 683x384, for minutes while the frame held 60 fps with GPU time to spare. A stale frame-start timestamp and event waits that idled the GPU made its timer read more than the frame took: [Dynamic resolution at its floor while the GPU has time to spare](../../../docs/reference/frame-rate.md#dynamic-resolution-at-its-floor-while-the-gpu-has-time-to-spare).
- Current: the launcher's **Dynamic resolution** (`DM_DYNAMIC_RESOLUTION`, off by default) holds full resolution. A stub of the frame step rule in [`patches.py`](patches.py), placed by the level function's fingerprint, makes that function return level 0 while state page `+0x40` is 0, so the update climbs to full size and stays there; 1 runs the game's own choice. The rewriter declares the `DYNAMIC_RESOLUTION` capability when it places the stub.
- Measured on the M4 Pro (20-core GPU, 2026-11-08, `kokiri-deck`, one run each): at full resolution (the main passes 1536x864 in pass dumps at 75, 100 and 125 s) 48.1 fps, frame p50 16.74 / p95 33.41 ms, GPU p50 15.0 / p95 16.9 ms: the GPU needs about one vsync a frame, so the frame step holds 2 vsyncs much of the time. With the game's own dynamic resolution and the host fixes above: 60 fps, GPU p50 12.6 ms, at a lower resolution. A second dynamic-resolution run wandered off the route into Saria's dialogue and is not counted.

- **Handheld mode.** Measured 2026-11-07: no memory saved beyond the spread (see the plan above). - **Render targets aliased as in the game's pool.** Done in item 4 (a heap per 32 MB span of GPU-only memory, not per pool; above). The game describes the storage of one GPU-only pool (flags 0x2a1) as many render targets: walking in Link's house, 5,409 new Metal textures (23.7 GB in all) in 3,300 frames, all COMPRESSIBLE 2D targets of 543 descriptions over 819 offsets. On NVN they share the pool's memory; here each description at each offset is a Metal texture of its own. A Metal placement heap that mirrors the pool, with textures at overlapping offsets aliasing, would bound the targets by the pool's size and remove the churn in the Open item above. `image_texture` already does this for one case (resolution families at one offset); the work is mapping NVN offsets to Metal's sizes and alignments. Keeping evicted targets for reuse instead was tried on oot-clean and made the walk slower there: it kept 370 MB more, and both of its runs fell to about 62 ms a frame against 28 ms without it (stan69b/nxnative a3df77e4; measured with the `GPU allocated` figure, which reads high on this game, see the Memory notes above).
- **Guest pages the CPU cannot read.** A CPU_NO_ACCESS pool's textures exist twice, in guest memory and as Metal textures, which costs twice on iOS. Releasing those guest pages after upload saves memory only where no shader reads the range as raw global memory ([textures made only when read](../../../docs/reference/memory.md#shaders-report-which-textures-they-read-through-a-pool) lists why it is not done).
- **Smaller textures on small devices.** Skipping the largest mip level of large streamed textures takes each to about a quarter, at a visible cost; a profile key for small devices, general.
- **Block-compressed textures kept compressed.** To check on the device: a format it cannot sample, decompressed to RGBA8, takes 4 to 8 times the memory.
- **The guest's 6.2 GB heap.** Only the pages it touches count; `mem_map_limit` gives freed ones back. How much of it the game dirties is not measured.

First step for an iOS build: a `vmmap -summary` / `footprint` split of a long Mac run, then the aliasing above, which also helps the Mac.

## Driving it on the Mac

Run headless, `DM_CTL` at a control file. The work folder has `boot.sh <secs> <log>` (with a guard that kills the host past 12.5 GB wired or 16 GB of swap; do not run without it), `ctl.sh`, `seq.sh`, `snap.sh`, `keys.sh <logs>` (adds and builds the keys the logs ask for), `white.py` (share of near-white pixels in a shot) and `run/save_ref` (autosaves in Kokiri Forest).

From an empty save: at about 45 s `A` (title), `A` (New Game), then the movie. From `save_ref`: at about 58 s `A~0.2`, 5 s later `A~0.2` (Load), 30 s later three `A~0.1` 3 s apart, then 12 s to the bridge outside Link's house. There `LUp~3.5`, `A~0.2` (Climb Down) and `LDown~4` three or four times reach the village floor.

## Open

- Root cause confirmed on M4 Pro (2026-11-08): [ignored event waits](../../../docs/reference/nvn-objects.md#gpu-event-waits-order-work-across-queues) let lighting consumers run before their producers. The game issues about 25 waits and 19 signals per frame. All 297 complete traced frames submit queue 5's ambient-cache consumer `9e6b00b050e30801` before queue 1's SH producer `21d9f83e6027c565`, despite the explicit dependency. Queue 1 also waits for the CPU frame-ready event after the CPU clears the lighting buffer. At frame 3872 the consumer ran at 0.686 ms, the clear at 0.966–0.968 ms, and the producer at 1.282 ms; its release followed at 4.467 ms. Exposure writer `1bba09ec4bc8ff67` has another event dependency. The native SDK's flush/invalidate functions are no-ops for these coherent pools.
- The pale outline around Link is produced before fog, bloom and upscaling, by task `efaa4fa6a80ba719`, mesh `066f5daf12e43c71`, fragment `5ad65c0eefd09c7f`. An offline replay matches both 768x432 RGBA16F targets byte for byte. Removing shared-buffer bytes 48–111 makes direct SH lighting agree with the cached ambient lookup (affected-pixel mean RGB error 0.100/0.136/0.218 falls to 0.0034/0.0020/0.0008): the cache lacked the SH contribution available to the later direct draw. Honoring the event dependency removes the outline, confirmed by the player and later captures.
- A repeating patchy pale layer remained after event ordering was fixed, including with optional attachment discard disabled. [Conditional rendering state lost across queue continuations](../../../docs/reference/rendering.md#conditional-rendering-survives-queue-continuations) caused repeated clears: disabled draws and pending timestamp counter values must survive physical Metal submission boundaries. Fixing both removes the layer in 2,000 asynchronous frames covering a stationary view, loading, camera rotation and movement to the village floor. The loading peak is the normal black-to-scene fade; the camera peak is a foreground branch crossing the view. These bounded samples do not establish every later area is unaffected. Synchronous screenshots wait for the GPU and can hide the original race, so validation uses asynchronous present copies. The rebased delivery subset passes the focused queue, descriptor, continuation, completion, residency and mesh-first-use checks. The current-main shader rebuild and five-game regression are still running at the visual-fix push.
- Diagnostic caveat: earlier shader probes used fragment buffer 30, which conflicts with alpha-test state, then buffer 28 with added atomics that can move depth testing late. Visual conclusions from those instrumented runs are inconclusive. The event trace, offline producer comparison and combined validation above use the original uninstrumented fragment libraries. The scene flash predates those probes.
- Regression reach is uncertain because every NVN submission now passes through logical queue scheduling. The five selected checks are Ocarina (the original dependency), Three Houses (multiple queues), Octopath Traveler 0 (command-buffer fences and Unreal RHI), Octopath Traveler II (an available boot route), and Okami HD (an older NVN path). The run is in progress; its unfinished rebuild is not a passing result. The focused tests pass with Metal validation: event/receipt 80, descriptor lifetime 38, continuation 38, native mesh first use 42 and storage-writer state 34 checks per encoding mode; capture 91, suspend 22, NVN 245, alias residency 28, completion ordering 36 in each of three configurations, and counter-overlap 42 per mode. The older CPU-post report/GPU-byte ordering limitation remains open as described in the rendering reference.

- Current on M4 Pro (20-core GPU, 2026-11-08, the `kokiri-deck` route in [`bench.tsv`](bench.tsv), the partial shader set): GPU p50 12.6 / p95 13.6 ms, 51.8 fps, frame p50 16.69 ms (60 fps most of the time; two runs). Before, the main pass sat at the game's floor, 683x384, and the frame step held 30 fps at 16.3 / 18.6 ms (a hold of one vsync needs a cost under 1.1 vsyncs, a probe back to it 0.85). The time was geometry: per frame about 9 ms in the vertex and mesh stages, 5 ms compute, 4 ms fragment (Metal System Trace); the foliage task/mesh pass 4.6 ms of vertex-stage time against 0.2 ms of fragment. Two causes, both general: the mesh shaders read their 128-bit raw loads a word at a time ([128-bit raw global loads read one word at a time](../../../docs/reference/shaders.md#128-bit-raw-global-loads-read-one-word-at-a-time), about 3.1 ms), and occlusion conditions were never read ([Occlusion conditions read once landed](../../../docs/reference/rendering.md#occlusion-conditions-read-once-landed), 0.6 ms). Ruled out by A/B: the mesh shaders' threadgroup memory (folding it 50-77% smaller did not help), its zero fill, the pool table reads, their primitive output (0.3 ms) and missing `c1_full.tsv` / `cb_extent.tsv`. Open: compute is still about 5 ms of the frame (the NDSR upscaler `d99fbeeb53d38847` writing 2048x1152, a fixed cost at any internal resolution, and a culling group), not looked into.
